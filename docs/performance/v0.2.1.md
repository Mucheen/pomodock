# v0.2.1 资源占用优化

2026-10-04，在 macOS arm64、Electron 44.3.0 上测量。基线为 `2c1439f`，两版均加载生产构建和独立空白数据目录。每个场景预热 4 秒，然后每 2 秒读取一次 `app.getAppMetrics()`，取 3 次平均。

内存为所有应用进程 `workingSetSize` 的和，单位 MiB。共享页面可能被重复计算，这与 Windows 任务管理器截图的内存列不是同一口径。指标定义见 [Electron MemoryInfo](https://www.electronjs.org/docs/latest/api/structures/memory-info)，测量 API 见 [app.getAppMetrics](https://www.electronjs.org/docs/latest/api/app#appgetappmetrics)。

| 场景 | 基线工作集 | 优化版第一轮 | 优化版第二轮 | 基线 CPU | 优化版第二轮 CPU |
| --- | ---: | ---: | ---: | ---: | ---: |
| 待机 | 351.8 | 332.3 | 421.6 | 0.1% | 0.0% |
| 展开计时 | 417.7 | 343.0 | 368.0 | 1.8% | 0.8% |
| 收起计时 | 406.0 | 346.1 | 371.6 | 1.6% | 0.0% |
| 收起暂停 | 370.8 | 282.6 | 373.0 | 0.1% | 0.0% |

第一轮未移除状态灯的持续动画，第二轮包含全部优化。工作集受系统压缩、缓存和回收时机影响，待机、暂停数据没有稳定改善；以上是短时样本，不代表长期上限，也不能推算 Windows 的内存降幅。计时样本减少约 34–75 MiB，但不作固定降幅承诺。

可复现的行为变化：

- 普通按钮点击不再创建 AudioContext。基线点击开始后存在第五个 Audio Service 进程，样本占约 40.7 MiB；优化版在正常计时中只有四个进程，响铃才创建音频上下文，关闭提醒后释放。操作系统可能延迟退出音频服务进程。
- 展开计时的后台状态消息从每 6 秒约 12 次降到 6–7 次；收起计时在本次 6 秒窗口内为 0 次，按分钟边界更新，最后一分钟按到时期限调度。
- 待机、暂停从每 500ms 轮询改为每分钟检查，午夜单独唤醒；唤醒电脑时立即检查实际期限。
- 状态消息不再携带 `dailyRecords`；打开日历才请求一次记录，关闭后渲染器释放该页面。
- 移除状态灯的无限动画，并恢复 Chromium 的后台节流。

关闭 GPU 硬件加速的实验工作集为 318.3 / 365.1 / 346.5 / 349.4 MiB，展开计时 CPU 为 1.6%；收益不稳定，最终保持默认硬件加速。

## 复测

```bash
npm run benchmark:memory
npm test
npm run test:smoke
```

`benchmark:memory` 输出每个场景的进程分类、内存、CPU 和消息次数。Windows 的每个进程还会输出 `privateMB`。原始状态和系统是否处于内存压力下均可能影响结果，请在同一电脑、同一口径下重复对照。

28 项单元测试覆盖每日统计、历史迁移、四轮循环、新刷新调度、精确到时和音频释放。实际 Electron 窗口测试验证收起后到时自动展开、音频上下文释放与日历读取。Windows 包在 macOS 上构建并核对内容，本次没有 Windows 真机内存测试。
